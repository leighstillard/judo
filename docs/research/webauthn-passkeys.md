# Research: passkey-per-approval — what WebAuthn concretely requires of judo

Resolves [judo#4](https://github.com/leighstillard/judo/issues/4). Primary sources: the W3C WebAuthn Level 3 spec ([w3.org/TR/webauthn-3](https://www.w3.org/TR/webauthn-3/), 26 May 2026 ed.); `webauthn-rs` on [docs.rs](https://docs.rs/webauthn-rs/latest/webauthn_rs/) (chiefly `Webauthn`, `WebauthnBuilder`, `AuthenticationResult`) and the kanidm repo/guide; 1Password's `passkey-rs` ([github.com/1Password/passkey-rs](https://github.com/1Password/passkey-rs)); MDN's [`CredentialsContainer.get()`](https://developer.mozilla.org/en-US/docs/Web/API/CredentialsContainer/get); and [passkeys.dev](https://passkeys.dev/docs/reference/terms/). Web/docs reading only; no system changes.

## The shape of the problem

A passkey ceremony has two halves that judo splits across two trust domains. The **page** (served by the relay, running in the human's phone browser) calls `navigator.credentials.get()` and returns a signed assertion. The **verifier** (the local daemon) checks that assertion. WebAuthn was designed assuming these are the same party — a website that both serves the login page *and* verifies the login. Judo pulls them apart: a dumb relay serves the page, the daemon holds the credentials and does the crypto. The good news, established below, is that WebAuthn verification is *pure crypto over signed bytes plus static config* — it needs no web server — so the split is sound. The sharp news is that splitting them surfaces one honest limitation (the relay serves the page JS, so it controls what the human *sees*) that shapes the whole protocol.

## 1. Library landscape — use `webauthn-rs`

**`webauthn-rs` (kanidm) is the answer for judo's Relying Party side.** It is the mature, widely-deployed Rust RP library (it backs kanidm's own IDM), and it is deliberately opinionated toward exactly judo's use case. Its API is framework-free: every function takes and returns plain serialisable types (`CreationChallengeResponse`, `RegisterPublicKeyCredential`, `RequestChallengeResponse`, `PublicKeyCredential`, `AuthenticationResult`) — no Actix/Axum/Rocket dependency, no async, no I/O. You serialise the challenge structs to JSON, ship them however you like, and hand the response structs back. That is precisely what a daemon-behind-a-relay needs.

The four load-bearing calls ([docs.rs `Webauthn`](https://docs.rs/webauthn-rs/latest/webauthn_rs/struct.Webauthn.html)):

```rust
fn start_passkey_registration(&self, user_unique_id: Uuid, user_name: &str,
    user_display_name: &str, exclude_credentials: Option<Vec<CredentialID>>)
    -> WebauthnResult<(CreationChallengeResponse, PasskeyRegistration)>
fn finish_passkey_registration(&self, reg: &RegisterPublicKeyCredential,
    state: &PasskeyRegistration) -> WebauthnResult<Passkey>
fn start_passkey_authentication(&self, creds: &[Passkey])
    -> WebauthnResult<(RequestChallengeResponse, PasskeyAuthentication)>
fn finish_passkey_authentication(&self, reg: &PublicKeyCredential,
    state: &PasskeyAuthentication) -> WebauthnResult<AuthenticationResult>
```

**RP-persisted state.** From registration, store the `Passkey` struct (public key, credential ID, counter, backup flags) — that is the enrolled credential. Between each `start_*` and its `finish_*`, store the returned `PasskeyRegistration` / `PasskeyAuthentication` state (docs: *"YOU MUST STORE THE PasskeyAuthentication VALUE SERVER SIDE"*); it carries the challenge and expected policy and is what makes the ceremony single-use and replay-resistant. `finish_passkey_authentication` returns an `AuthenticationResult` with `counter() -> u32`, `needs_update() -> bool`, `user_verified() -> bool`, `backup_state()`/`backup_eligible()` ([docs.rs `AuthenticationResult`](https://docs.rs/webauthn-rs/latest/webauthn_rs/prelude/struct.AuthenticationResult.html)) — when `needs_update()` is true, write the new counter back onto the stored `Passkey`.

**The three type families.** `webauthn-rs` exposes `Passkey`, `SecurityKey`, and `AttestedPasskey` as distinct builder flows so you can't misuse one for another. `Passkey` = any modern authenticator (platform TouchID/FaceID/Android, roaming keys, synced credentials), user-verification required, attestation not demanded — the right default for judo. `SecurityKey` is the older "second-factor hardware token" model. `AttestedPasskey` additionally demands and verifies attestation (proof of authenticator make/model against metadata) — enterprise device-restriction territory, more state and policy than judo wants for v1. **Judo uses the `Passkey` flow.**

**Static-binary fit.** `webauthn-rs` is pure Rust with no C linkage, so it drops straight into judo's single static daemon (unlike the sudo plugin `cdylib` from [judo#3], this adds no FFI). It is not `no_std`, but the daemon isn't either — irrelevant here.

**Alternatives, ruled out.** `passkey-rs` (1Password) is a fine library but the *wrong side of the wire*: it implements the **authenticator/client** (CTAP2 + a software authenticator + `passkey-client::Client`), i.e. the thing that *creates* assertions, not the RP that *verifies* them ([passkey-rs README](https://github.com/1Password/passkey-rs/blob/main/README.md)). It would only matter if judo wanted to *be* a passkey, which it doesn't. `webauthn-rs-core` is the lower-level crate under `webauthn-rs`; only reach for it if the opinionated `Passkey` flow proves too rigid — it won't for v1.

## 2. The RP ID / origin problem — the crux

WebAuthn binds every credential to an **RP ID**, and the client (browser) enforces that the *origin* running the ceremony is the RP ID or a registrable-domain suffix match of it (W3C §4 "Relying Party Identifier", enforced in the §5 create/get algorithms). Concretely, `WebauthnBuilder::new(rp_id, rp_origin)` requires *"rp_id must be an effective domain of rp_origin"* and warns *"rp_id can NOT be changed without breaking all of your users' associated credentials"* ([docs.rs `WebauthnBuilder`](https://docs.rs/webauthn-rs/latest/webauthn_rs/struct.WebauthnBuilder.html)). A page at `https://approve.judo.dev` may use `rp_id = "judo.dev"` (or `"approve.judo.dev"`, or `"dev"` — but `"dev"` is a public suffix and browsers reject public-suffix RP IDs, the one PSL gotcha).

**The reassuring half: the verifier need not be the web host.** `finish_passkey_authentication` takes only the stored `PasskeyAuthentication` state and the `PublicKeyCredential`, and checks the signature, the challenge, and the origin/rp_id *from the daemon's static `WebauthnBuilder` config* — it makes no network call and needs no web server. So judo's daemon verifies with `rp_id = "judo.dev"` and expected `rp_origin = "https://approve.judo.dev"` while the relay merely served the bytes. This is fully supported and is the linchpin that makes the whole relay-splits-from-verifier architecture legal WebAuthn.

Three deployment options, and **who can phish/forge under each**:

- **(a) RP ID = the shared relay domain (`judo.dev`), page on `approve.judo.dev`.** Simplest; one enrollment works everywhere. Credentials are *bound to `judo.dev`* — if the user later self-hosts a relay on their own domain, the old credentials won't work there (re-enrollment required; `rp_id` is immutable). Phishing surface: only a page served under a `judo.dev` origin can even *invoke* a ceremony for these credentials — the browser's origin check means `evil.com` cannot. So the relay operator's control of `judo.dev` is load-bearing (see the honest limitation below).
- **(b) Per-user subdomains (`alice.judo.dev`) with `rp_id = "judo.dev"`.** Allowed: the spec's rule is that RP ID must be a registrable-domain suffix of the origin's effective domain, and `judo.dev` is a suffix of `alice.judo.dev`. In `webauthn-rs` this needs `WebauthnBuilder::allow_subdomains(true)`, which explicitly permits *"`https://au.idm.example.com` to be valid when configured as `https://idm.example.com`"*. PSL gotcha: this only holds while `judo.dev` is a single registrable domain — if judo ever put users on a domain that appears on the public suffix list (so each user's subdomain is a *separate* registrable domain), cross-subdomain scoping breaks. Keep `judo.dev` off the PSL.
- **(c) Self-hosted relay on the user's own domain — `rp_id` per install.** Best isolation (no shared-domain blast radius, no dependence on the judo.dev operator) at the cost of one `rp_id` per deployment and re-enrollment when moving. This is the option for the security-maximalist self-hoster.

**What a malicious relay can and cannot do — the "what you see is what you sign" constraint.** The relay serves the page's JavaScript. It therefore *cannot forge an approval* — the assertion is signed by a key the relay never holds, and the signature covers `clientDataJSON` including the exact challenge, so a malicious relay cannot obtain a valid assertion for a challenge the daemon didn't issue, and (per §3) the daemon binds each challenge one-to-one to a specific command envelope. **But** the relay controls the pixels: it can serve JS that renders *"Approve: list files"* while the daemon's challenge actually corresponds to *"rm -rf /"*. The human verifies the passkey, the daemon gets a cryptographically valid assertion for the destructive command, and releases it. Crypto integrity held; human intent was subverted. This is the single sharpest finding of this ticket. It cannot be fixed by signatures alone; it requires that **what the human reads is derived from the same bytes the challenge commits to, and that the human actually reads it.** Candidate mitigations, feeding [judo#7]:
  1. **Command echo in the out-of-band notification.** The ntfy/Slack push (which does *not* transit the relay's page JS) carries the human-readable command summary. The human compares the notification text against the page before approving. Cheap, no crypto, but relies on the human looking — accept-with-echo.
  2. **Page content pinned / integrity-checked.** Serve the approval page as a fixed, versioned static asset with Subresource Integrity, or serve it *from the daemon through a tunnel* so the relay never touches the HTML/JS — the relay degrades to a pure notification+envelope pump. Strongest, but complicates the "dumb relay at a stable domain" story.
  3. **Render the command strictly from the signed payload, client-side, in pinned JS.** Only as trustworthy as the JS delivery, so it collapses back into (2).

The honest statement for the spec: with a shared hosted relay (options a/b), **the relay is trusted for page integrity even though it is untrusted for approval forgery.** The notification-echo (mitigation 1) is the minimum viable defence and should ship in the skeleton; tunnel-served page (mitigation 2) is the hardening path for the paranoid/self-hosted tier.

## 3. Challenge binding — daemon keeps a challenge→envelope map

The WebAuthn challenge is opaque random bytes (spec: ≥16 bytes / ≥100 bits entropy, base64url in `clientDataJSON`; W3C §4, §6.1.1). The tempting design — `challenge = hash(approval_envelope)` so the binding is intrinsic — is **not** how `webauthn-rs` works: `start_passkey_authentication` *generates the challenge internally* and the caller cannot inject one (confirmed from the signature — it takes only `&[Passkey]` and returns the `RequestChallengeResponse` with the library-chosen challenge). So judo uses the **server-side association** pattern: when a privileged command arrives, the daemon calls `start_passkey_authentication`, then stores `challenge (from the state) → approval_envelope` in a TTL'd map alongside the `PasskeyAuthentication` state. On `finish_*`, `webauthn-rs` verifies the assertion's challenge matches the stored state (single-use, replay-protected by consuming the state); the daemon then looks up which envelope that challenge was bound to and releases *that* command. The binding lives in judo's map, enforced by the daemon consuming state exactly once — not in the challenge bytes. (If intrinsic hash-binding is ever wanted, drop to `webauthn-rs-core`, which exposes challenge construction — not needed for v1.)

## 4. Enrollment flow and the synced-passkey threat model

**Enrollment.** Daemon calls `start_passkey_registration(user_id, name, display, None)` → serialises `CreationChallengeResponse` → relay → page calls `navigator.credentials.create()` → authenticator mints the credential → `RegisterPublicKeyCredential` returns via relay → daemon calls `finish_passkey_registration` → stores the `Passkey`. One-time setup, ideally done once on the phone that will approve.

**Synced vs device-bound — the threat-model wrinkle.** A **synced passkey** (iCloud Keychain, Google Password Manager) *replicates across the user's devices* (passkeys.dev: a discoverable credential *"available through real-time syncing across devices, backup restoration, cross-device exercise"*); a **device-bound passkey** (FIDO2 security key) *"is bound to a single authenticator"*. For judo this means: with a synced passkey, the approval capability appears on *every device signed into that cloud account*, and its security reduces to the account's security. That is usually acceptable (it's how the user's own logins work) but must be stated: **judo's approval key is as strong as the cloud account it syncs to**, and a security-maximalist should enroll a device-bound key. **Counter implications:** synced passkeys generally report `signCount = 0` always — the spec (§6.1.1) already says the counter *may validly be zero* and warns that clone-detection via counters is unreliable for multi-device credentials. `webauthn-rs` handles this: `AuthenticationResult::counter()` returns 0 and `needs_update()` stays false for such credentials, so judo must **not** treat a non-incrementing counter as an attack — only act on a *regression* below a previously-seen non-zero value. Persist `backup_state()`/`backup_eligible()` for audit, but don't gate on them.

**Cross-device (hybrid/CaBLE).** The QR-scan hybrid flow exists for approving on a phone when the ceremony started on a *desktop*. Judo largely sidesteps it: the notification lands *on the phone directly*, so the phone both opens the link and holds the passkey — a same-device ceremony, no QR hop. Hybrid only re-enters if the human opens the approval link on a device lacking the credential; nice to support, not required for the skeleton.

## 5. The approval page, minimally

A single static HTML file with vanilla JS: fetch the options JSON from the relay, `navigator.credentials.get({ publicKey, ... })`, POST the assertion back. No framework, no build step, inlineable. **HTTPS is mandatory** — WebAuthn is a Secure-Context-only API (MDN). **User activation:** the default *modal* `get()` (not conditional UI) is what judo wants — conditional mediation (`mediation: "conditional"`) is the autofill flow and is not applicable here. The spec doesn't hard-require transient activation for `get()`, but Safari and increasingly Chrome expect the call to originate from a user gesture, so drive `.get()` from a button click ("Review & Approve") rather than firing on load — which also gives the human the beat in which to read the command (see §2). Web-push/PWA packaging is a later nicety; for the skeleton the ntfy notification carries the link and the page is a plain URL.

## Recommendation

- **Library:** `webauthn-rs`, `Passkey` flow, verification in the daemon. Framework-free plain types, pure static Rust, no web server on the verifier — a clean fit for the daemon-behind-relay split.
- **RP ID scheme:** ship with **option (a)** — `rp_id = "judo.dev"`, page on `approve.judo.dev`, `allow_subdomains(true)` so per-user subdomains (option b) work without re-enrollment. Document **option (c)** (self-host, `rp_id` per install) as the isolation-maximalist path, and state plainly that credentials are immutably bound to their `rp_id` so moving domains means re-enrolling. Keep `judo.dev` off the public suffix list.
- **Challenge binding:** daemon-side TTL'd `challenge → envelope` map plus the stored `PasskeyAuthentication` state; the library owns the challenge, judo owns the association and enforces single-use by consuming state once.
- **The constraint to carry into the protocol:** what-you-see-is-what-you-sign. A malicious/compromised relay cannot forge an approval but *can* lie to the human about what they're approving. Minimum defence: echo the exact command in the out-of-band notification (which bypasses the relay's page JS) so the human can cross-check; hardening: serve the page from the daemon through a tunnel so the relay never controls the pixels.

## Pointers into adjacent tickets

- **Protocol ([judo#7](https://github.com/leighstillard/judo/issues/7)):** the relay carries five opaque blobs and understands none of them — registration options/response, auth options/response, all base64url JSON. It needs TLS at a stable domain and the challenge→envelope routing key; it must *not* see credentials or be able to mint challenges. The daemon persists the `Passkey` store, the `challenge→envelope` + `PasskeyAuthentication` map with TTL, and enforces single-use (replay protection is consuming the state exactly once). Bake in the **what-you-see-is-what-you-sign** rule: notification-command-echo is mandatory, tunnel-served-page is the documented hardening.
- **Lifecycle ([judo#6](https://github.com/leighstillard/judo/issues/6)):** challenge/envelope entries need a TTL and a timeout-≠-deny disposition (mirrors the Hermes finding); a `PasskeyAuthentication` state that expires unused is a clean deny. Renotify/renewal interacts with challenge single-use — a re-notify must mint a *fresh* challenge, not replay the old one.
- **Policy schema ([judo#8](https://github.com/leighstillard/judo/issues/8)):** the passkey tier is one rung of the danger ladder; the `hardline` floor sits above it (no passkey overrides deny). "Which credential/enrollment approves which workspace" is policy vocabulary worth pinning early.
- **Spec ([judo#10](https://github.com/leighstillard/judo/issues/10)):** encode the RP-ID option matrix (a/b/c), the immutability-of-`rp_id` caveat, the synced-vs-device-bound threat note (approval key inherits cloud-account strength), and the relay-trusted-for-page-integrity honesty up front.
- **Skeleton ([judo#11](https://github.com/leighstillard/judo/issues/11)):** `webauthn-rs` `Passkey` flow + a single static HTML/JS approval page + ntfy notification carrying the link *and* the command echo. Same-device ceremony (phone gets the push, phone holds the passkey) — no hybrid/QR needed for the demo.
